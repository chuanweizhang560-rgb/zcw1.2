# ZCW 电力巡检多无人机研究工作流

版本：`v0.1`

状态：待执行前确认

## 0. 已确认的边界

下面这些点已经确认，不再作为争议项：

1. 根目录使用 `1.2_zcw`。
2. 仓库从零开始，不沿用任何现有 `BS` 项目的实现代码。
3. 任务范围只保留两类：
   - 风机巡检
   - 电缆巡检
4. 仿真和控制优先复用公开成熟方案，不自己手搓低层飞控。
5. 多无人机默认以 4 架为目标规模，后续可扩展。
6. 第一版策略不直接输出电机量，只输出角色和任务级指令。
7. 线缆巡检必须包含“线缆追踪/重捕获”机制，而不是只做航点飞行。
8. 线缆巡检第一版主线采用 `PCL RANSAC + catenary/spline + Frenet/pure pursuit`。
9. 电缆场景接受“公开电塔/风机模型 + 参数化导线”的组合，不要求所有对象都来自同一个仓库。
10. 只要存在成熟、可适配、许可证兼容的开源方案，就不自行编写核心算法或模型，最多只做接口适配、参数配置和工程集成。
11. 允许并要求后续执行 agent 主动检索 GitHub、官方文档、论文主页和相关网页，筛选、克隆并评估公开开源仓库作为依赖、参考或替代实现。
12. **不依赖 Gazebo 真值定位**。所有无人机通过开源 SLAM 方案（如 ORB-SLAM3 / VINS-Fusion / DroidSLAM）自主定位，不使用 `/gazebo/link_states` 或其他仿真内置真值进行控制闭环。
13. **所有核心算法必须采用成熟开源实现**，不自研任何核心算法（包括但不限于：定位、建图、SLAM、规划、控制、RL、感知）。自研代码严格限定在接口适配、参数配置、工程集成和实验编排。如果找不到足够成熟的开源方案，必须记录在 `PROCESS_LOG.md` 中，不得私自替代。

## 1. 设计原则

1. 先可跑，再变强。
2. 先规则 baseline，再学习策略。
3. 先单机闭环，再多机协同。
4. 先复用公开模型和公开算法，再考虑自定义扩展。
5. 所有关键决策都要能在日志里复现。
6. 环境真实感和物理稳定性分层处理，不能互相绑死。
7. 遇到成熟开源实现时，优先采用并记录来源，不自行发明核心算法。
8. **SLAM 优先，真值辅助**：所有控制闭环必须基于 SLAM 估计位姿，Gazebo 真值仅用于评估和调试。

## 2. 技术总边界

### 2.1 控制边界

第一版建议采用下面的分层：

| 层级 | 责任 | 频率建议 | 备注 |
|---|---|---|---:|---|
| 策略层 | 角色分配、任务分配、目标区选择 | `1 Hz` | 只输出高层决策 |
| 任务层 | 风机/电缆的动作原语生成 | `1-2 Hz` | 可事件触发重规划 |
| 轨迹层 | 航点平滑、短时轨迹插值 | `10-20 Hz` | 用成熟轨迹库 |
| 感知层(SLAM) | 自定位 + 增量建图 | `10-30 Hz` | 开源 SLAM（无真值） |
| Offboard 心跳 | 保持 PX4 处于外部控制模式 | `>= 2 Hz`，建议 `20 Hz` | 必须持续发送 |
| PX4 内环 | 姿态、位置、速度稳定 | PX4 内部 | 不自研 |

这里的核心原则是：

- `RL` 不直接输出连续电机控制。
- `RL` 也不直接承担高频控制闭环。
- `RL` 只对角色和任务做决策，实时性由 PX4 和成熟轨迹/控制接口保障。

### 2.2 推荐接口

优先采用：

- PX4 官方 ROS 2 接口
- `OffboardControlMode`
- `TrajectorySetpoint`
- `px4_ros_com`

原因很直接：

- PX4 官方文档明确要求 offboard 需要连续 `2Hz` 以上的 proof-of-life。
- ROS 2 接口比直接自己拼 MAVLink 逻辑更适合后续维护。

参考：

- [PX4 Offboard 模式](https://docs.px4.io/main/en/flight_modes/offboard.html)
- [PX4 ROS 2 Offboard Control](https://docs.px4.io/main/en/ros2/offboard_control.html)
- [PX4/px4_ros_com](https://github.com/PX4/px4_ros_com)

## 3. 仿真底座

### 3.1 第一版推荐

第一版默认使用：

- `PX4 SITL`
- `ROS 2 Humble`
- `Gazebo 11`

这样做的原因是：

1. 当前机器已经具备 ROS 2 Humble 和 Gazebo 11。
2. 我们的首要目标是尽快把研究链路跑通，不先做平台迁移。
3. PX4 对多机仿真有成熟支持，ROS 2 接口也有公开示例。

参考：

- [PX4 Simulation](https://docs.px4.io/main/en/simulation/index.html)
- [PX4 Multi-Vehicle Simulation](https://docs.px4.io/main/en/simulation/multi-vehicle-simulation.html)
- [PX4 Multi-Vehicle Simulation with ROS 2](https://docs.px4.io/main/en/ros2/multi_vehicle)

### 3.2 资产来源

模型和世界优先从以下来源选：

1. [Gazebo Fuel](https://gazebosim.org/docs/latest/fuel/)
2. [PX4-gazebo-models](https://github.com/PX4/PX4-gazebo-models)

### 3.2.1 外部仓库检索与克隆授权

本仓库执行阶段，默认允许后续 agent：

2. 筛选可用的公开开源仓库、模型包、算法实现和仿真资源。
3. 将确认可用的外部仓库克隆到本仓库预留的外部依赖目录。
4. 记录每个外部依赖的来源、许可证、版本和用途。

执行约束：

1. 只用成熟、开源、可适配的项目作为基础。
2. 不自行编写核心算法，不自行从零造模型。
3. 自定义代码只用于集成、适配、封装和参数调整。
4. 如果找不到足够成熟的开源方案，必须在 `PROCESS_LOG.md` 里说明，不得私自替代。

### 3.3 环境颗粒度

环境不采用单一精度，而是分四层：

| 层 | 表示方式 | 精度目标 | 用途 |
|---|---|---|---|
| 视觉层 | 公开 mesh / 纹理 | 尽量真实 | 给相机和展示用 |
| 碰撞层 | 简化 primitive / capsule / box | 稳定优先 | 给物理仿真和避障用 |
| 规划层 | 栅格 / 安全走廊 / 中心线 | 0.5-1.0 m 级 | 给任务规划和跟踪用 |
| 语义层 | `turbine / tower / cable / corridor / no-fly` | 任务级 | 给策略和评估用 |

这意味着：

- 风机可以是视觉真实、碰撞简化。
- 电缆可以不一定用超复杂 mesh，但必须有可靠的几何中心线和安全走廊。
- 地形不追求每个沙粒都真实，只需要对飞控、视线和避障有足够约束。

## 4. SLAM 与建图架构

### 4.1 定位原则

整个项目**不依赖 Gazebo 真值**进行控制闭环。无人机通过开源 SLAM 方案实现自主定位：

- 每架无人机运行独立的 SLAM 实例（单机定位）
- 初始位姿已知（基站坐标），后续全凭 SLAM 推算
- SLAM 输出：6-DOF 位姿 + 局部/全局地图
- 推荐候选方案（最终选型需调研后确定）：
  - `ORB-SLAM3` — 单目/双目/RGB-D + IMU，ROS 2 集成成熟，学术标准
  - `VINS-Fusion` — 双目 + IMU，紧耦合，已用于多机场景
  - `DroidSLAM` — 深度学习 SLAM，鲁棒性更高但计算量更大

### 4.2 建图架构

地图从空开始，由多机增量构建：

1. **全局地图表示**：所有无人机共享同一张全局地图
2. **地图类型**：3D 体素占用网格或 TSDF（根据 SLAM 输出格式确定）
3. **建图流程**：
   - 初始时地图为空，仅已知基站坐标
   - 每架无人机通过 SLAM 不断更新自身位姿
   - 探测到的新区域/障碍物融入全局地图
   - 地图作为 RL 策略的观测输入
4. **多机融合**：各机将各自 SLAM 子图合并为全局地图
5. **更新频率**：`1-2 Hz` 供规划层使用，`10-30 Hz` 供 SLAM 内部

### 4.3 传感器配置

Gazebo 中每架 Iris 无人机需挂载：

| 传感器 | 用途 | 备注 |
|---|---|---|
| 双目立体相机 | SLAM 视觉输入、障碍感知 | Gazebo MultiCamera 插件 |
| IMU | SLAM 惯导融合 | PX4 SITL 内置 |
| GPS（可选） | 辅助定位 / 故障降级 | Gazhao GPS 插件 |

### 4.4 SLAM 与控制的耦合

```
SLAM 位姿 → 坐标变换 → MAVROS / PX4 定位源
              ↓
         任务层 / 轨迹层 (基于 SLAM 位姿)
              ↓
         Offboard 心跳 → PX4 位置设定点
```

- SLAM 输出作为 `mavros/local_position/pose` 或自定义 `geometry_msgs/PoseStamped`
- PX4 的 EKF2 可配置为使用外部视觉位姿（`EKF2_AID_MASK=24`）
- **严禁**在控制链路中使用 `/gazebo/link_states` 作为位置源

## 5. 场景构造规则

### 5.1 场景范围

第一版建议只做荒漠风机场 + 输电线路，不引入光伏。

建议的场景要素：

- 沙漠地形
- 若干风机
- 若干电塔
- 电缆/导线
- 基站起飞区
- 备用中继区
- 安全返航区

### 5.2 障碍物颗粒度

障碍物按三类处理：

1. 大型刚体
   - 风机塔筒
   - 电塔
   - 基站建筑
   - 这些物体使用稳定的碰撞体

2. 细长结构
   - 电缆
   - 导线
   - 这类结构用参数化曲线描述，不强求高复杂度碰撞网格

3. 地形和随机障碍
   - 沙丘
   - 小型石块
   - 临时设施
   - 只在规划层保留足够分辨率

### 5.3 推荐初始参数

下面这些先作为第一版默认值，后续可以调：

| 参数 | 建议值 | 说明 |
|---|---:|---|
| 全局规划网格 | `1.0 m` | 大范围调度 |
| 局部规划网格 | `0.5 m` | 电缆/风机近距离跟踪 |
| 电缆安全横向距离 | `5.0 m` | 作为最小侧向保护带 |
| 风机塔筒安全半径 | `8.0-12.0 m` | 视模型大小再定 |
| 风机高度分层 | `3` 层 | 低、中、高三圈巡检 |
| 轨迹重规划周期 | `1.0 s` | 任务层更新 |
| Offboard setpoint 频率 | `20 Hz` | 保持外部控制稳定 |

## 6. 风机巡检工作流

风机巡检按“靠近 - 环绕 - 分层 - 退出”执行。

### 6.1 基础动作原语

1. 接近航段
   - 从安全距离进入目标风机外圈。

2. 环绕巡检
   - 以塔筒中心为圆心做圆周或螺旋轨迹。
   - 相机或观测方向始终朝向目标。

3. 分层扫描
   - 低、中、高三层各走一圈。
   - 每层维持稳定横向距离。

4. 退出段
   - 从塔体周围安全撤离到下一任务点或中继位。

### 6.2 轨迹生成

第一版建议：

- 任务层给出风机中心点和巡检高度带
- 轨迹层用成熟轨迹库平滑
- PX4 负责最终执行

如果需要精细轨迹平滑，优先考虑：

- `mav_trajectory_generation`
- 或者同类公开 minimum-snap 轨迹库

参考：

- [mav_trajectory_generation](https://github.com/ethz-asl/mav_trajectory_generation)

### 6.3 覆盖判定

风机任务不靠图像分类结果判断完成，而采用几何覆盖逻辑：

1. 目标面离散为 surfel 或采样点。
2. 判断采样点是否落入视锥体。
3. 判断是否被遮挡。
4. 累加有效覆盖率。

成功标准建议：

- 单个风机覆盖率达到阈值
- 轨迹无碰撞
- 进入和退出段稳定
- offboard 不掉线

## 7. 电缆巡检工作流

电缆巡检是整个项目里最需要细化的部分，不能只靠“飞到附近看看”。

### 7.1 电缆巡检的两种模式

#### 模式 A：已知先验模式

适用于：

- 事先知道电塔坐标
- 线路走向有先验
- 场景中导线几何可由塔位推断

处理方式：

1. 根据电塔和导线连接关系生成中心线先验。
2. 用参数化曲线表示导线。
3. 生成贴线巡检走廊。
4. 无人机沿走廊飞行并保持偏移距离。

#### 模式 B：线缆重捕获模式

适用于：

- 目标线段被遮挡
- 先验失效
- 需要从点云里重新找线

处理方式：

1. 以电塔和最近已知导线点为锚点建立 ROI。
2. 对点云做地面去除和离群点滤波。
3. 用线模型拟合候选导线。
4. 若失败，进行局部扫掠重捕获。

### 7.2 电缆追踪算法主线

第一版建议采用“几何优先”的公开算法组合：

1. 点云预处理
   - ROI 裁剪
   - 体素下采样
   - 地面滤波
   - 离群点去除

2. 导线候选提取
   - 使用 `PCL` 的 RANSAC 线模型
   - 必要时做分段线段提取

3. 中心线重建
   - 如果导线是悬链线，优先做 `catenary` 拟合
   - 如果点云稀疏，使用分段样条拟合
   - 如果塔位明确，可用塔间约束修正中心线

4. 局部跟踪
   - 用 Frenet frame 计算横向误差、前向误差和高度误差
   - 用 look-ahead / pure pursuit 生成下一段跟踪点
   - 保持固定横向偏移，避免贴线过近

5. 失锁处理
   - 进入搜索状态
   - 在预测中心线周围做扇形或平行扫描
   - 超过阈值后退回上一个安全锚点

参考：

- [PCL Sample Consensus](https://pointclouds.org/documentation/group__sample__consensus.html)
- [PCL Line Model](https://pointclouds.org/documentation/classpcl_1_1_sample_consensus_model_line.html)

### 7.3 电缆巡检的安全约束

电缆场景必须额外引入这些约束：

1. 塔体禁飞区
   - 电塔周围设置硬禁飞半径

2. 导线安全走廊
   - 围绕导线中心线建立横向安全带

3. 转塔保护区
   - 导线从一个塔过渡到另一个塔时，轨迹必须有平滑连接段

4. 失锁回退区
   - 线缆识别失败时必须有回退逻辑，不能原地抖动

### 7.4 电缆巡检的验收指标

建议至少记录：

- 线缆跟踪误差
- 横向偏移最大值
- 失锁次数
- 重捕获成功率
- 与塔体最小距离
- 任务完成时间
- offboard 断流次数

## 8. 多机协同设计

### 8.1 角色集合

第一版固定以下角色：

1. `INSPECT`
   - 执行风机或电缆巡检

2. `RELAY`
   - 充当中继节点

3. `EXPLORE`
   - 负责地图探索和补盲

4. `RESERVE`
   - 低电量或待命

### 8.2 调度逻辑

策略层输出：

- 当前角色
- 目标任务
- 目标区
- 是否需要中继
- 是否需要重规划

建议的动作结构示例：

```text
{
  role: INSPECT | RELAY | EXPLORE | RESERVE,
  task_id: turbine_01 | cable_segment_03 | relay_point_02,
  waypoint: [x, y, z, yaw],
  corridor_id: optional,
  valid_for_sec: 1.0
}
```

### 8.3 通信拓扑与地图共享

多机通信不直接追求"永远全连通"，而是追求"关键任务不断链"。

建议在第一版明确：

- 基站是根节点
- 至少保留一条可到达基站的多跳链路
- 深入远端的机体必须有最近中继节点
- 中继节点电量低于阈值时要可切换
- **全局地图共享**：各机通过基站或 DDS 共享 SLAM 地图更新
- 地图共享频率：`0.5-1 Hz`（带宽受限时增量同步）

### 8.4 多编队扩展

初期固定 1 个编队（4 架无人机=INSPECT+RELAY+EXPLORE+RESERVE）。
后期扩展目标：

- 每编队固定 4 机角色组合
- 多编队时增加跨编队协调层
- 编队间通过基站进行地图合并和高层任务协调

## 9. 学习层设计

### 9.1 学习层职责

学习层只负责：

- 角色分配
- 任务排序
- 目标区域选择
- 中继位置选择
- **探索 vs 任务权衡**：基于当前地图覆盖率和任务进度决策

学习层不负责：

- 姿态内环
- 电机控制
- 高频轨迹插值

### 9.2 推荐算法

第一版学习算法建议采用：

- `MAPPO`
- centralized critic
- decentralized actor

同时保留一个单机 `PPO` baseline，专门用于：

- 验证单机任务是否可学
- 排查奖励函数是否有问题
- 做与多机协同的对照实验

原因：

- 多机协同任务天然适合集中训练、分散执行
- 后续容易切换到更复杂的 reward shaping
- 单机 baseline 可以把“环境问题”和“多机问题”分开排查

### 9.3 RL 观测空间

RL 策略的观测（每个智能体）建议包含：

1. **自身状态**：SLAM 位姿 (x, y, z, yaw)、速度、剩余电量
2. **任务状态**：当前任务进度、目标风机/电缆位置（地图坐标系）
3. **地图输入**：局部或全局占用网格的编码（如降采样 + CNN 特征或向量化）
4. **队友状态**：其他无人机的 SLAM 位姿（通信可及时）
5. **地图覆盖率**：已建图区域 vs 总可探索区域比例

### 9.4 RL 输出频率

建议默认：

- `policy inference`: `1 Hz`
- `task replan`: 事件触发 + 至少 `1 Hz`
- `state aggregation`: `1-2 Hz`
- `offboard setpoint`: `20 Hz`

这个频率设计的好处是：

1. 策略层不会过快抖动。
2. 低层飞控持续稳定。
3. 角色切换和任务重分配有足够响应时间。
4. 频率分层后，策略层可慢、执行层可快，便于训练和调试。

### 9.5 奖励项

建议奖励项分成五类：

1. 任务奖励
   - 风机覆盖率提升
   - 电缆跟踪有效前进

2. 探索奖励
   - 地图熵下降
   - 新区域被确认
   - 地图覆盖率增量

3. 通信奖励
   - 连通性保持
   - 中继链路稳定

4. 安全惩罚
   - 碰撞
   - 过近塔体
   - offboard 掉线
   - 电量过低

5. 协同奖励
   - 多机地图重叠避免（奖励探索不重复的区域）
   - 任务切换效率

### 9.6 训练阶段

训练分五步：

1. 单机 SLAM + 建图验证（手动飞行）
2. 单机规则 baseline 巡检 + SLAM 定位
3. 单机 PPO（带地图观测）
4. 双机协同 + 地图共享
5. 四机完整协同 + MAPPO + 共享地图

每一步都必须先过规则 baseline，再进入 RL。

### 阶段 0：仓库骨架

交付物：

- 风机模型候选清单
- 电塔模型候选清单
- 线缆表示方案
- 场景引用清单

验收：

- 每个资产都有来源和许可证信息
- 没有“临时手画模型”进入主线

#### 1.1 资产清单要求

每个候选资产必须记录以下信息：

- 名称
- 来源链接
- 许可证
- 尺寸范围
- 是否可直接用于 Gazebo 11
- 是否带碰撞体

#### 1.2 第一批优先清单

优先调研的资产类型：

- 风机塔筒和叶片
- 输电杆塔
- 导线 / 电缆
- 沙漠地形
- 起飞平台 / 基站区域

### 阶段 2：仿真环境最小闭环

交付物：

- PX4 SITL 启动脚本
- 单机 offboard 样例
- Gazebo 场景

验收：

- 车辆能起飞
- `OffboardControlMode` 心跳稳定
- 场景无崩溃

#### 2.1 最小闭环要求

这一步只要求形成以下闭环：

1. ROS 2 节点能启动。
2. PX4 能进入 offboard。
3. 车辆能稳定悬停。
4. 能收到位置或速度设定点。
5. 能记录日志。

这一步不要求完成巡检任务，也不要求多机协同。

### 阶段 3：单机风机巡检

交付物：

- 风机巡检状态机
- 分层环绕轨迹
- 覆盖率统计

验收：

- 能稳定完成单个风机巡检
- 不碰撞
- 指标可记录

#### 3.1 单机风机巡检子阶段

1. 仅环绕，不做图像识别。
2. 仅单层环绕，不做多层。
3. 再扩展到三层高度带。
4. 最后加入覆盖率统计。

### 阶段 4：单机电缆巡检

交付物：

- 导线中心线表达
- 线缆追踪器
- 重捕获逻辑

验收：

- 能沿线飞行
- 能通过塔位过渡
- 线丢失后能恢复

#### 4.1 电缆追踪子阶段

1. 用公开导线中心线先验飞一遍。
2. 用点云线拟合做离线验证。
3. 把拟合结果作为在线中心线。
4. 再加入重捕获。
5. 最后加入失锁回退。

### 阶段 5：双机中继

交付物：

- 一机巡检、一机中继
- 拓扑维持逻辑
- 通信断链告警

验收：

- 深入区域时仍能保持回传
- 中继角色可切换

#### 5.1 双机职责拆分

1. 1 号机优先巡检。
2. 2 号机优先中继或补盲。
3. 断链时可以互换职责。

### 阶段 6：四机协同

交付物：

- 角色分配器
- 任务队列
- 多机状态聚合

验收：

- 4 架机能稳定协同
- 任务不冲突
- 关键链路不断

#### 6.1 四机初始分工建议

1. 1 号机：风机巡检主机。
2. 2 号机：中继主机。
3. 3 号机：电缆巡检主机。
4. 4 号机：补盲 / 备用 / 动态接力。

### 阶段 7：RL 接入

交付物：

- 多智能体环境封装
- MAPPO 训练脚本
- 评估脚本

验收：

- baseline 能稳定复现
- RL 训练能跑起来
- 结果可比较

#### 7.1 接入顺序

1. 先跑规则 baseline。
2. 再跑单机 `PPO`。
3. 再跑多机 `MAPPO`。
4. 最后才做奖励整形和协同增强。

### 阶段 8：SLAM 开源方案调研与集成

交付物：

- SLAM 方案调研记录（候选对比、选型理由）
- 选定 SLAM 的 ROS 2 集成（传感器配置、位姿输出）
- SLAM 输出替代真值作为控制输入

验收：

- UAV 基于 SLAM 位姿稳定悬停/移动
- 控制链路完全断开 Gazebo 真值
- 定位误差在可接受范围内

### 阶段 9：增量建图 + 多机地图共享

交付物：

- 全局地图表示（体素/栅格）
- 增量建图节点
- 多机地图同步机制

验收：

- 地图从空开始，飞行中逐步填充
- 多机地图可合并
- 地图可作为 RL 观测

### 阶段 10：完整链路集成（SLAM + 建图 + 任务 + MAPPO）

交付物：

- 全栈：SLAM → 建图 → 任务控制器 → MAPPO
- 共享地图作为 RL 观测
- 探索 vs 任务调度实验

验收：

- 4 机在沙漠场景中完成巡检 + 建图
- 无真值闭环
- 指标可比较

## 12. 仍需你最终拍板的点

下面这几个点会直接影响第一版实现，我建议在动手前最后确认一次：

## 13. 执行与仓库管理约定

这一节是给后续执行 agent 的操作规则，不是技术方案。

### 13.1 Git 与 GitHub

1. 仓库地址固定为：
   - `https://github.com/chuanweizhang560-rgb/zcw.git`
2. 后续执行过程中由 agent 自行管理 git：
   - 自行查看状态
   - 自行创建/切换分支
   - 自行整理提交
   - 自行判断何时需要 push
3. 所有重要阶段都应保留 git 记录，便于回滚和审计。
4. 如 push 失败或远端权限异常，必须停止并报告具体错误，不要绕过。

### 13.2 截图与可视化验证

1. 需要对仿真、RViz、Gazebo 画面进行截图验证。
2. 当需要做视觉检查时，优先使用真实运行中的仿真截图，不用纯示意图。
3. 截图的用途包括：
   - 检查场景是否正确加载
   - 检查模型是否缺失或错位
   - 检查无人机是否悬停、起飞、巡线
   - 检查 RViz 中的轨迹、地图、传感器话题是否正常显示
4. 若截图发现异常，先记录现象，再决定是否进入下一步，不要默认跳过。

### 13.3 执行反馈规则

1. 实现过程中若遇到平台、依赖、权限、运行崩溃、仿真错误，必须明确反馈。
2. 不要为了继续推进而隐式改掉方案边界。
3. 关键决策点要先记录在文档或日志中，再继续执行。

### 13.4 根目录文件约定

1. 进程记录文件必须放在仓库根目录，固定为 `PROCESS_LOG.md`。
2. 文档、记录、检查清单类的新建文件，默认优先放在仓库根目录，避免散落到新的深层目录。
3. 实现代码、配置、资产、数据仍然按约定目录存放，不打散到根目录。
4. 外部克隆仓库统一放入 `third_party/`，不直接散落在根目录。
